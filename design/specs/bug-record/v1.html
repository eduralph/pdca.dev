Spec: Bug record -- v1

Normative specification. Status: DRAFT (unstable -- will change). This document uses RFC 2119 keywords: MUST, SHOULD, MAY.

Motivation

The bug track (ADR-0020) carries a bug from a public issue to a draft pull request through several stages, run by different leaves, possibly from different vendors, on different machines (ADR-0021). The bug record is what passes between them. It has to be written down for three reasons:

  • It is the handover between untrusted and trusted places. Every stage after Summarize reads the record instead of the issue, and the record is the only thing the driver takes from a produce job besides the bytes of a test or a diff (ADR-0021 §1). What it may contain must therefore be a rule a program checks, not a prompt. Its sanitization is hygiene, not a security boundary: it stops literal copying, not steering, and the design does not rely on it to keep a steered leaf from doing harm.
  • It separates what a model says from what the driver decides. Leaves describe the bug and write the test; the driver records results, the target ref and routing. That split holds only if it is part of the format.
  • It outlives a run. A track can stay open across an instance's copier update, so a record written by one release of the driver must be read correctly, or refused, by the next.

Scope

This specification defines the bug record document: its encoding, its fields, which stage writes each section, the validation a reader performs, how a leaf hands its part over, and how the driver detects a record it did not write.

It does not define:

  • the directory a record is kept in, which ADR-0020 section 8 decides, or how it relates to the bundle format (bundle-format/v1, planned in #712);
  • the issue form a reporter fills in; section "Intake" below says only what Summarize may take from it;
  • the stage logic, triggers, target-ref choice and protected paths, which ADR-0020 decides. This spec gives them fields, not rules.

Conventions

  • A record is one JSON document per bug, encoded as UTF-8 and conforming to I-JSON (RFC 7493): no duplicate member names, no unpaired surrogates, numbers within IEEE 754 double precision.
  • A writer produces or changes a record; a reader parses and validates one. The driver is both. A leaf reads the record (never the issue) and produces only the fragment its stage owns (see "Ownership").
  • Text fields are strings meant for people. Identifier fields are strings matched against a fixed pattern.
  • A ref is a Git branch name, written without refs/heads/ (for example main, release/0.1), matching [A-Za-z0-9][A-Za-z0-9._/-]{0,127} and containing no ... A commit is a full 40-character lowercase hexadecimal object ID. A tag follows the ref pattern. Whenever the driver passes one of these to git, it does so after --end-of-options.
  • Text is compared after Unicode normalization form NFKC and case folding.
  • "Absent" means the member is not present. null is allowed only where this spec says so.

Requirements

1. Top level

A record MUST be a JSON object with exactly these members:

Member Type Written by Meaning
format string, exactly "pdca.bug-record" driver Identifies the document type
version integer, exactly 1 driver This specification's version
source object (§2) driver Where the bug came from
summary object (§3) Summarize leaf, validated by the driver The sanitized description
reproduction object (§4) or null Reproduce leaf (test) and driver (the rest) The red test and its results
target object (§5) or null driver Where the fix goes
routing object (§6) or null driver Whether a cycle may start without a maintainer
closure object (§13) or null driver How the track ended; null while it runs

A reader MUST reject a record with a member missing, a member not listed here, or a member of the wrong type. This holds at every level of the document: v1 has no extension members.

reproduction, target, routing and closure are null until their stage has run. A record in which target is not null MUST have a non-null reproduction whose status is "reproduced"; one in which routing is not null MUST have a non-null target.

2. source

Member Type Meaning
kind "issue" or "scheduled-run" An issue in the tracker, or a failing test from the instance's own scheduled runs (ADR-0020, stage 4)
repository string, owner/name The repository the bug is filed against
issue integer ≥ 1, or null The issue number; MUST be non-null when kind is "issue" and null otherwise
run string of 1–128 characters from [A-Za-z0-9._-], or null The scheduled run's ID; MUST be non-null when kind is "scheduled-run" and null otherwise
issue_digest 64 lowercase hexadecimal characters, or null SHA-256 of the issue text Summarize was given (below); MUST be non-null exactly when kind is "issue"
attempt integer 1–9 Which attempt of Summarize and Reproduce this record holds (ADR-0020 section 11)

The issue text is the UTF-8 encoding of: the issue title, one line feed, the issue body and, from the second attempt on, one line feed and each comment by the reporter since the track's questions, in order, each followed by one line feed. When the driver truncates the text it gives Summarize (summary.truncated), the digest is of the truncated text, and the truncation is a cut after a fixed number of bytes set per instance, so it can be repeated. Every comparison in §3 is against this text.

3. summary

The summary is the only part of the record derived from text a stranger wrote.

Member Type Limit Meaning
title text 1–120 characters One line naming the defect
description text 1–600 characters What goes wrong, in plain language for someone who does not know the code
impact text 1–600 characters Who is affected and what it costs them (lost data, a wrong result, a crash, a slowdown)
observed text 1–1500 characters What happens
expected text 1–1500 characters What should happen instead
trigger text 1–1500 characters The conditions under which it happens
areas array of 1–2 identifier strings from the instance's configured area list Where the leaf believes the defect lives; informational, never used for routing (ADR-0020 section 5)
reported_ref object The version the reporter saw the bug on (below)
truncated boolean true if the leaf had to shorten the issue text it was given

reported_ref has two members:

  • kind: "ref", "tag", "commit" or "none".
  • value: a ref, a tag or a commit as defined in "Conventions", matching kind; null when kind is "none". A reader MUST reject a value that does not match the pattern.

Sanitization. The driver MUST validate every text field of summary before it writes the record, and MUST reject the leaf's output, never repair it, when a text field fails any rule below. Text is normalized (NFKC, case-folded) on both sides first. A word is a maximal run of letters and digits; a token is a maximal run of non-whitespace characters with leading and trailing punctuation (.,;:!?()[]{}"') removed.

  • It contains a run of five or more consecutive words that also appears in the issue text.
  • It contains a number of three or more digits that also appears in the issue text.
  • It contains a token of eight or more characters that also appears in the issue text and that contains a digit, one of . / _ : = @ +, or two or more hyphens (a likely identifier, path, host name, token or repository name).
  • It contains a URL, a Markdown link or image, a code span or fence, an HTML tag, or an @-mention.
  • It contains a character of Unicode category Cc other than line feed, or of category Cf (zero-width and bidirectional controls), or a character outside the Basic Latin, Latin-1 Supplement and General Punctuation blocks that the issue text does not also contain.

These are the reason-field rules of ADR-0017 section 5 (including its edge-punctuation stripping and its "also appears in the issue" condition for identifiers), extended to the whole summary and to the comments a later attempt reads. They make the summary say what kind of thing fails, never which literal input makes it fail; the Reproduce leaf rediscovers the literals from the code. They do not stop a summary from carrying an instruction in plain words; nothing downstream treats the summary as more than a description, and the design's safety does not rest on these rules (ADR-0021 §1). When the leaf's output is rejected, the driver MAY ask the leaf once more and otherwise stops the track for the issue with needs-triage.

reported_ref. The driver MUST check that a reported_ref other than "none" names a ref, tag or commit that exists in source.repository, and MUST replace it with {"kind": "none", "value": null} when it does not. A leaf's guess never becomes a ref the driver checks out.

4. reproduction

Member Type Written by Meaning
status "reproduced", "flaky" or "not-reproduced" driver A test that fails on every verify run, one that fails only on some, or none within the stage's budget (ADR-0020 section 9)
test object (below), or null Reproduce leaf (kind, path, seed), driver (sha256) The test; MUST be non-null exactly when status is "reproduced" or "flaky"
signature string, or null driver Where the test failed, <path>:<line>, as the verify job's PDCA-FAILURE-AT: marker reported it; null when the marker was absent or status is not "reproduced". Informational: it links tracks and never closes one (ADR-0020 section 10)
results array of result objects (below) driver The verify job's outcome on each candidate ref; at least one when status is "reproduced" or "flaky"
questions array of 0–5 text strings, each 1–300 characters Reproduce leaf, validated by the driver What the reporter would have to tell; MUST be empty unless status is "not-reproduced"

signature's path part is relative to the repository root, uses /, and is neither absolute nor contains ..; it may point anywhere in the tree, since a failure is usually in source, not in the test. The line is a decimal integer ≥ 1. The marker is printed by the test under test, so the signature is a hint, not a fact.

questions are posted to the public issue. The driver MUST apply the sanitization rules of §3 to them.

test:

Member Type Meaning
kind "unit", "property" or "simulation-seed" What kind of test it is
path string The test file, relative to the repository root, using /; MUST NOT be absolute or contain .., and MUST lie under one of the instance's configured test directories
sha256 64 lowercase hexadecimal characters The SHA-256 of the test file's bytes as the driver took them from the Reproduce job
seed string of 1–64 characters from 0-9, A-Z, a-z, - and _, or null The seed the test runs with; MUST be non-null exactly when kind is "simulation-seed". Always present, null when it does not apply

The record names no command: the command that runs a test of each kind is instance configuration, and the driver passes it path (and seed) as arguments after --end-of-options or its equivalent. The driver MUST compute sha256 itself from the bytes it took, not take a leaf's value, and every verify job runs exactly those bytes (ADR-0021 §1); a diff that changes the file at path makes the C4 row unverifiable (ADR-0020, stage 5).

A result object:

Member Type Meaning
ref ref or tag, or null The candidate ref the test ran on, or the reported version (below); null only for a reported commit
commit commit The commit ref pointed to at the time
runs integer 1–100 How many times the verify job ran the test on this ref, each on a fresh copy of the tree
failures integer 0–runs How many of those runs failed
outcome "red", "green", "flaky" or "error" Derived from the counts, or could not run (build failure, infrastructure)

outcome MUST be "red" exactly when failures equals runs, "green" exactly when failures is 0, and "flaky" otherwise, unless it is "error"; an "error" result has failures 0. An "error" outcome is not evidence either way. Results are listed in the order they were run; a ref MUST NOT appear twice.

The results cover every candidate ref and, when summary.reported_ref is not "none" and names something other than a candidate ref, one more result for the reported version: ref is the reported ref or tag, or null for a reported commit, and commit is what it resolved to. That result is evidence only (ADR-0020 section 4): it can be the red leg and it can lead to "answer-only", but it is never a fix target. A result with a null ref MUST have a commit equal to summary.reported_ref.value.

5. target

Member Type Meaning
decision "fix-on-main", "backport-existing", "fix-on-release" or "answer-only" The outcomes of ADR-0020 section 4 ("fix-on-release": the fix is built on the release branch, because bisection did not finish or the instance sets release first)
ref ref, or null Where the fix is built or backported first; null only for "answer-only"
backports array of refs Further release branches that get a backport cycle; empty unless decision is "fix-on-main" or "backport-existing", or merge_forward is true
merge_forward boolean, optional (absent means false) Whether the release branch in ref then merges forward to main under release first; MUST be false unless decision is "fix-on-release", and when true, main MUST appear in reproduction.results with outcome "red"
fixing_commit commit, or null The commit on main found by bisection; MUST be non-null exactly when decision is "backport-existing"
answered_release string of 1–64 characters, or null The first release in which the test is green; MUST be non-null exactly when decision is "answer-only"

Every ref in ref and backports MUST appear in reproduction.results with outcome "red", and MUST be a branch: the reported version's result never names a target unless the reported ref is itself a candidate ref.

6. routing

Member Type Meaning
protected boolean Whether the test file's path or any path the diff touches is in the instance's protected paths
matched array of strings The protected-path patterns that matched; empty exactly when protected is false
start "auto" or "maintainer" Whether Fix starts on its own or the bundle pull request opens with the test only (ADR-0020 section 3)

start MUST be "maintainer" when protected is true. Routing is computed from the test path when the test is verified and again when a diff exists; it may move from "auto" to "maintainer", never back. Nothing a leaf writes is an input to it.

7. Ownership

The record mirrors ADR-0017's rule that the model classifies and the code decides:

  • A leaf's output for its stage MUST be a JSON object holding only the members that stage writes: summary for Summarize; test (without sha256) and questions for Reproduce. The driver MUST reject leaf output with any other member, before validating content. Both members are always present: a found test comes with questions [], and a test not found is test null with 0–5 questions. A non-null test together with non-empty questions is rejected, not dropped.
  • source, reproduction.status, reproduction.signature, reproduction.results, test.sha256, target, routing and closure are written only by the driver, from the verify job's output or facts it established itself. Nothing in them comes from a produce job's output (ADR-0021 §1).
  • Once reproduction.status is "reproduced" or "flaky", a writer MUST NOT change summary or reproduction.test. A changed bug is a new record.
  • A record with reproduction.status "not-reproduced", closure null and source.attempt below the instance's limit is waiting on the reporter (ADR-0020 section 11). A new attempt replaces summary and reproduction, increases source.attempt by one and recomputes source.issue_digest over the issue text as the new attempt read it. After the last attempt the driver writes closure.

8. Intake

The issue form of an instance's repository SHOULD ask for the version or commit the reporter used. Summarize MAY derive summary.reported_ref from that answer, subject to the check in §3. Nothing else from the form has a field of its own; it reaches the record only through the sanitized text fields.

9. Leaf output

A leaf hands over its part as one file with a fixed name in its output directory: summarize.out.json for Summarize, reproduce.out.json for Reproduce. The file MUST be a single JSON document as in "Conventions" and MUST hold only the members of §7.

The driver MUST read that file and nothing else. It MUST NOT extract JSON from a leaf's standard output, from a transcript, or from prose around a code block. A missing file, an empty file or a file that does not parse means the stage failed; it is never read as an empty result.

10. One record per file, Markdown only rendered

A record is stored as its own file, bug-record.json, holding exactly one record. It is never embedded in another document and records are never concatenated.

Any Markdown about a bug (the bundle's README.md, the cycle's brief, comments on the issue) is rendered from the record by the driver. A writer MUST NOT read state back from such Markdown; the record is the only source. This keeps the bug track out of the problem risk R5 describes, where state lives in model-written Markdown that every reader parses.

11. Integrity

Every stored record is accompanied by a MAC file, bug-record.json.mac, next to it.

  • The MAC file holds exactly one line: hmac-sha256 <key-id> <mac>, fields separated by one space, ended by one line feed. <key-id> is 1–64 characters from [A-Za-z0-9._-]; <mac> is 64 lowercase hexadecimal characters.
  • <mac> is HMAC-SHA256 (RFC 2104) over the exact bytes of bug-record.json. There is no canonical form: changing any byte, including whitespace, changes the MAC.
  • The key is a secret of at least 32 random bytes, held only on the workflow host and identified by <key-id> so it can be rotated. It MUST NOT reach a runner, a leaf, a repository or a log.
  • The driver MUST write the record and then its MAC on every change, and MUST verify the MAC before using a record. A missing MAC file, an unknown key ID or a mismatch stops the track with a NEEDS-HUMAN item. The driver MUST NOT repair or re-MAC a record that failed verification.
  • Leaf output (§9) carries no MAC: leaves hold no key. The driver validates it, merges it into the record and writes a new MAC.

A MAC, not a signature: the driver both writes and reads records, so a shared secret suffices, and HMAC is in the standard library the driver is limited to (ADR-0008).

12. Publication

A record and its MAC file are committed to the pdca repository, which may be public (ADR-0020 section 8). Writers MUST therefore put nothing in a record that is not fit to publish. The rules of §3 keep issue text out; in addition, no member may hold a secret, a signed URL, a host name or path of the workflow host, or an identifier of the runner's infrastructure. A published MAC reveals nothing about the key.

13. closure

Member Type Meaning
reason "accepted", "rejected", "delegated", "answered", "not-reproduced", "flaky", "withdrawn" or "handed-over" How the track ended (ADR-0020 sections 6, 7 and 11)
bundle_pull_request integer ≥ 1, or null The bundle pull request on the pdca repository; non-null exactly when reason is "accepted", "rejected" or "delegated"
pull_requests array of integers ≥ 1 The draft pull requests opened on the target repository after accept; non-empty only when reason is "accepted", and MAY be empty there until publish has run
linked_to array of integers ≥ 1 Issues whose open track shared this one's signature (ADR-0020 section 10); informational

A closure MUST agree with the rest of the record: "accepted" and "rejected" need a target whose decision is not "answer-only"; "delegated" needs reproduction.status "reproduced" and routing.start "maintainer" or a Fix that exhausted its budget; "answered" needs a target whose decision is "answer-only"; "not-reproduced" and "flaky" need reproduction.status with the same value. "withdrawn" and "handed-over" may close a record at any stage. A record with a non-null closure is changed once more at most, to fill pull_requests after publish; otherwise never.

Versioning and compatibility

  • A reader MUST reject a record whose format is not "pdca.bug-record" or whose version it does not implement. It MUST NOT guess.
  • Any change to a member, a type, a limit, a sanitization rule or an ownership rule is a new version. v1 has no compatible extensions.
  • A driver that implements a later version SHOULD keep reading v1 records until no open track holds one, so a track started before a copier update can finish. A driver that cannot read a record MUST stop that track with a NEEDS-HUMAN item rather than restart it.

Conformance

A conforming reader MUST accept every record under vectors/v1/valid/ and reject every record under vectors/v1/invalid/, for the reason given in the matching .reason.txt.

The sanitization rules of §3 compare a summary against the issue it came from, so their vectors live apart, under vectors/v1/sanitization/. Each record there is structurally valid and comes with the issue text as <name>.issue.txt. A conforming summary validator MUST accept every record under sanitization/accept/ and reject every record under sanitization/reject/, for the reason in its .reason.txt.

Leaf-output vectors live under vectors/v1/leaf-output/: files named as §9 requires, under accept/ and reject/ with a .reason.txt each. A conforming driver MUST accept every file under accept/ as that stage's output and refuse every file under reject/.

Integrity vectors live under vectors/v1/integrity/. test-key.txt holds a key for tests only, as hexadecimal, with key ID test-1. A conforming driver MUST accept the record under accept/ with its MAC file and MUST refuse every record under reject/, for the reason in its .reason.txt.

Vectors are part of this version: changing, adding or removing one after v1 is stable is a spec change (ADR-0018).

Open questions

  • [OPEN] Whether bug-record.json becomes one of the files the bundle-format spec (#712) defines, or stays a document of its own next to the cycle bundles.
  • [OPEN] Whether the thresholds of §3 (five words, three digits, eight characters) are right for summaries, which are longer than ADR-0017's reasons and may reject useful descriptions more often.
  • [OPEN] Whether the PDCA-FAILURE-AT: marker should be replaced by the test runner's structured output (for example cargo test's JSON) where one exists, to make signature less dependent on what the test chooses to print.
