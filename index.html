PDCA Harness turns each AI-driven contribution into one Plan → Do → Check → Act cycle. A deterministic driver does the work; a human stays at the three touch points that matter — authoring the spec, signing off the check, and improving the process.

What it is

A prepared harness, not tribal knowledge.

An AI model can write a plausible fix for almost any issue in seconds — which is exactly the danger. A plausible diff is not a verified one, and at volume the maintainer becomes both the bottleneck and the only safety net. PDCA Harness funnels AI-generated contributions through a quality cycle so each one arrives scoped, proven, and ready to sign off.

Render the Copier template into a new project, concretize it to your tracker, branches, and gates once, and a deterministic driver advances every contribution through a file-derived state machine — stopping only where a human is irreducible.

How it works

One contribution, one cycle.

PLAN   ◆  author the brief — the spec every beat is measured against
  │
  ▼
DO        a headless builder writes the patch + a red→green test
  │
  ▼
CHECK  ◆  deterministic gates (red→green) + a decorrelated reviewer,
          then the human verdict — accept · iterate · discontinue —
          and a draft PR the harness never marks ready
  ┊
ACT    ◆  every N cycles: recurring misses → new gates · rules · fields
  └──▶ back to a better-baselined PLAN

◆  a beat with a human touch point — everything else is automated
  • PlanAuthor the brief. A precise, field-structured spec every later beat is measured against. Human touch point #1.
  • DoBuild against the spec. A headless builder writes the patch, a shipped test, and its rationale — and can't mark a PR ready or merge it.
  • CheckVerify it, then decide. Deterministic gates (red→green), a decorrelated reviewer, and the irreducibly human judgments — folded into one SUMMARY with an explicit NEEDS-HUMAN checklist. The human completes Check at sign-off: accept, iterate (rebuild or re-spec), or discontinue — and accept is refused while anything is unresolved. An accepted bundle publishes as a draft PR the harness never marks ready. Human touch point #2.
  • ActImprove the process. Across cycles, recurring misses become new gates, brief fields, and rules — a better baseline every time. Human touch point #3.

Why it holds up

Correctness as the headline, not a vibe.

The one thing allowed to block a sign-off is a deterministic, LLM-free check: a test that is red before the fix and green after it. Everything a gate can't adjudicate — an ambiguous-scope lint, an environmental failure, the irreducibly human judgments — surfaces as an explicit checklist for a person, never silently passed or silently blocked.

  • No LLM in the gating pathBlocking a sign-off requires a deterministic red→green proof — not a model's say-so. The reviewer can't block on its own: what it can't settle goes on the human's NEEDS-HUMAN checklist.
  • The builder can't shipThe Do leaf edits code, runs tests, and may push a draft PR — but it can never mark a PR ready or merge it.
  • Draft PR by defaultAn accepted fix publishes as a draft — a human is always the one who marks it ready.
  • Resumable by constructionState lives in files, not a database. A cycle pauses at a human touch point and resumes later, and one planning session can brief several issues that build unattended and queue for sign-off, cheapest reviews first.
  • Provable before you spendA full cycle rehearses entirely offline — stub models, stub gates, no network — so you can learn the state machine and prove the plumbing before a single token.

Key features

Built for a backlog, not a single fix.

  • Parallel processingMany issues at once. Do and Check run unattended across parallel lane workers — each with its own git worktree and $PDCA_LANE slot — while Plan, sign-off, and Act stay serial, so the human touch points never fork.
  • Dependency resolutionOrder computed, not hand-run. Declare Depends on: / Conflicts with: and the scheduler levels the batch deterministically — conflicting bundles split into different waves, and an unschedulable graph (a cycle, an unknown prereq) is rejected before any build.
  • Dependency wavesA whole chain in one run. Each wave's accepted work lands on a run-scoped integration branch the next wave builds on, so a B-needs-A batch ships as a reviewable PR stack — the harness pushes, it never merges. pdca waves previews the plan.
  • Per-issue model selectionThe right backend per fix. Route a bundle's builder by a brief field (Difficulty: high → a frontier model) or pin it explicitly (Do model: keeps a sensitive fix local). Issues in one wave can run on different models; a repeatedly-failing one escalates.
  • Structured verificationThree axes, one verdict. Correctness as a chain, conformance as a stack, validation as one indivisible judgment — with a red→green proof as the only thing allowed to block and the human judgments on an explicit NEEDS-HUMAN checklist.

How it is built

Documented the way it asks you to document.

The harness keeps the four document classes it gives every rendered project: a living architecture overview, append-only decision records, proposals that move from draft to accepted, and specifications under change control — all in the repo, all published here. The project's governance and code of conduct sit beside them.

Get started

Render it, prove it offline, wire in your repo.

copier copy gh:eduralph/pdca-harness my-pdca   # render the harness
cd my-pdca && make install                      # bootstrap the tools
.venv/bin/pdca flow TOY --rehearse              # one full cycle — offline, zero tokens

The rehearsal runs stub models and stub gates — no network, no tokens — so you can learn the state machine before a single real beat. If make install linked pdca onto your PATH, plain pdca works too. When it feels solid, step 01 wires it to your tracker, branches, and gates.
